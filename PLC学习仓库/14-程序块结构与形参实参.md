# 14 - 程序块结构与形参实参

> 从本章开始，我们进入第四章【高级指令】的学习。这一章不学新的"指令"，而是学一个更重要的能力：**如何把程序写得又整洁、又能反复复用**。打个比方：前几章你学的是一个个"汉字"（指令），从本章开始，你要学怎么"写文章"（搭程序结构）。这一步跨出去，你就从"会写代码"升级到"会做工程"了。

## 📖 学习目标

1. 能说出把程序拆分成多个程序块的两大好处：**代码复用**和**结构清晰**；
2. 掌握 OB、FC、FB、DB 四种程序块的定义、作用和区别，知道 OB1、OB100、OB30 各自在什么时刻执行；
3. 理解形参与实参的关系，掌握 Input、Output、InOut、Static、Temp、Return 六种参数类型的含义和使用场景；
4. 能在 TIA Portal 中独立完成 FC/FB 的参数定义与调用；
5. 理解多重背景（Multi-instance）的用途并掌握配置方法，最终用 FB 完成电机控制逻辑的封装。

## 一、为什么需要程序块

### 1.1 一个真实场景：10 台电机的"复制粘贴噩梦"

假设你负责一个车间，里面整整 10 台电机，每台都要做同样的三件事：

- 按下启动按钮 → 电机运行并自锁；
- 按下停止按钮 → 电机停止；
- 出现故障信号 → 电机立即停止，并点亮故障灯。

如果所有逻辑都从头写到尾地堆在 OB1 里，程序会变成这样：

```
OB1（不使用程序块的写法）
网络 1~3    ：电机1 的启停自锁、输出、故障处理
网络 4~6    ：电机2 的启停自锁、输出、故障处理
网络 7~9    ：电机3 的启停自锁、输出、故障处理
   ……
网络 28~30  ：电机10 的启停自锁、输出、故障处理
```

30 个网络长得几乎一模一样，只有变量名不同。这会带来一连串问题：

1. **改一处要改十处**：如果客户要求"故障时还要让蜂鸣器响 3 秒"，你要找齐 10 个地方逐个修改，漏一处就是 bug；
2. **查找困难**：程序几千行，想知道"电机7 的逻辑在哪"要翻半天；
3. **容易抄错**：复制粘贴时忘改变量名，电机7 启动却让电机8 转起来，这种错误最难查。

### 1.2 程序块 = 乐高积木

解决思路很简单，就像小学生都会的总结公式：与其每道题都从头推导，不如**把方法总结成一个公式，以后套用**。

在 PLC 里，这个"公式"就是**程序块**：把"电机启停控制"这套逻辑封装成一块积木，写一次，然后哪里需要就在哪里"拼"（调用）一次。

好处一目了然：

| 好处 | 说明 | 对应上面的例子 |
| ---- | ---- | ---- |
| 代码复用 | 一段逻辑只写一次，可调用任意多次 | 10 台电机 = 1 个块 + 10 次调用 |
| 结构清晰 | 每个块只负责一件事，像书的目录 | 看 OB1 就知道整个设备分几大功能 |
| 易于维护 | 改一处，所有调用处同时生效 | 故障逻辑只改块内 1 次 |
| 便于分工 | 不同工程师可以各写各的块 | A 写电机块，B 写报警块 |

### 1.3 模块化程序的整体样子

```
                     ┌────────────────────────────────┐
                     │             CPU                │
                     │                                │
                     │   ┌────────┐                   │
    CPU 上电时 ──────►│   │ OB100  │  启动时执行一次    │
                     │   └────────┘                   │
                     │   ┌────────┐                   │
    循环执行 ────────►│   │  OB1   │  主程序            │
                     │   └───┬────┘                   │
                     │       │ 在 OB1 中调用           │
                     │   ┌───┴────┐   ┌─────────┐     │
                     │   │ FB 电机 │   │ FC 报警  │    │
                     │   └────────┘   └─────────┘     │
                     └────────────────────────────────┘
```

### 1.4 在 TIA Portal 项目树中看到的程序块

```
项目树
└── PLC_1 [CPU 1511-1 PN]
    ├── 程序资源
    │   ├── 添加新块              ← 在这里创建新的 FC / FB / OB
    │   ├── Main [OB1]            ← 主程序组织块（默认自带）
    │   ├── 电机控制 [FB1]        ← 我们编写的函数块
    │   ├── 电机控制_DB [DB1]     ← FB1 调用时生成的背景数据块
    │   ├── 报警处理 [FC1]        ← 我们编写的函数
    │   └── 公共数据 [DB2]        ← 我们建立的全局数据块
    └── ……
```

## 二、四种程序块的定义和作用

西门子 1500 PLC 的用户程序由四种块组成：OB、FC、FB、DB。下面逐个认识。

### 2.1 OB（Organization Block）组织块——"领导"

OB 是操作系统与用户程序之间的接口，**由 PLC 自动调用**，用户不能在程序里手动"调用"某个 OB。它回答的问题是："我的程序**什么时候**执行？"

常见 OB 类型：

| OB 类型 | 常用编号 | 什么时候执行 | 典型用途 |
| ---- | ---- | ---- | ---- |
| 主程序 OB | OB1 | 循环执行：执行完立刻从头再来，周而复始 | 放主要的控制逻辑，几乎所有程序都有它 |
| 启动 OB | OB100 | CPU 从 STOP 切换到 RUN 时执行一次 | 上电初始化：清零计数值、恢复默认状态 |
| 循环中断 OB | OB30 | 每隔固定时间执行一次（在 OB 属性里设定，如 100 ms） | 对时间要求严格的任务，如 PID 调节、高速采样 |

三种 OB 的执行时序：

```
CPU 上电
   │
   ▼
执行 OB100（启动块，只执行一次）
   │
   ▼
进入 RUN 模式
   │
   ▼
┌───────────────────────────────────────┐
│ OB1：读输入 → 逐条执行程序 → 写输出      │◄── 执行完立刻重来，
└──────────────────┬────────────────────┘    周而复始（循环扫描）
                   │ 每到设定时间（如每 100ms）
                   ▼
          插入执行一次 OB30，做完再回 OB1 继续
```

初学阶段，90% 的逻辑写在 OB1 里就够了；需要"开机只做一次"的初始化放 OB100。

### 2.2 FC（Function）函数——"计算器"（无记忆）

FC 的特点：**没有记忆**。它处理完数据就把结果交出去，完全不记得上次调用时发生了什么。

类比：计算器。你按 `1 + 1 =`，它显示 2；关掉再开，它什么也不记得。

技术特征：

- 没有 Static（静态存储）区；
- 没有背景数据块，调用时不生成 DB；
- 数据来了就算，算完就"忘"。

适合装：单位换算、数值计算、纯逻辑判断等**与历史状态无关**的内容。

### 2.3 FB（Function Block）函数块——"有记事本的员工"（有记忆）

FB 的特点：**有记忆**。它自带一个 Static（静态存储）区，数据保存在一个专属于这次调用的"背景数据块"里，下次调用时数据还在。

类比：空调。同一个牌子的空调，客厅那台记着 26 度制冷，卧室那台记着 24 度送风——每台空调有自己的"记忆"，互不干扰。

技术特征：

- 有 Static 区，静态数据存放在背景 DB 中；
- 每次调用 FB 都要指定一个背景 DB（相当于给这次调用配一个"记事本"）；
- 适合控制"有状态的设备"：电机（运行中/已停止）、阀门（已开/已关）、气缸（伸出/缩回）。

### 2.4 DB（Data Block）数据块——"仓库"

DB 本身不含程序，纯粹存放数据。它分两种，区别必须搞清楚：

| 对比项 | 全局 DB | 背景 DB |
| ---- | ---- | ---- |
| 归属 | 不属于任何块，是"公共仓库" | 属于某一次 FB 调用，是"私人仓库" |
| 谁能访问 | 所有块都能读写它 | 原则上只由对应的 FB 使用 |
| 怎么创建 | 手动"添加新块 → 数据块" | 在 OB1 中调用 FB 时自动生成 |
| 里面有什么 | 自己手动建的变量 | FB 接口中的 Input/Output/Static 等自动生成 |

```
            ┌────── 全局 DB「公共数据」 ──────┐
            │  温度值  计数值  生产数量 ……    │
            └──────── 谁都可以存取 ─────────┘
                  ▲           ▲           ▲
             OB1  │      FC1  │      FB1  │

    FB1 第 1 次调用 ──► 背景DB「电机1_DB」← 电机1 的私有数据
    FB1 第 2 次调用 ──► 背景DB「电机2_DB」← 电机2 的私有数据
```

### 2.5 四种块一览表

| 块类型 | 中文名 | 谁来调用它 | 有无记忆 | 有无参数接口 | 典型用途 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| OB | 组织块 | PLC 操作系统 | —— | 无 | 程序入口、启动初始化、定时中断 |
| FC | 函数 | OB / FB / FC 中调用 | 无 | 有（Input/Output/InOut/Temp/Return） | 计算、换算、通用逻辑 |
| FB | 函数块 | OB / FB / FC 中调用 | 有（存在背景 DB） | 有（Input/Output/InOut/Static/Temp） | 电机、阀门、气缸等设备控制 |
| DB | 数据块 | 被其他块读写 | 它本身就是数据 | 无 | 集中存放变量、保存配方和记录 |

### 2.6 何时选 FC，何时选 FB（决策指南）

先问自己三个问题：

```
问题1：这段逻辑需要"记住"上一次的状态吗？（比如电机现在是否在运行）
        │
   ┌────┴─────┐
   是         否
   │          │
   ▼          ▼
  用 FB      问题2：这段逻辑会用在多个设备/多处地方吗？
                   │
             ┌─────┴─────┐
             是          否（只在一处使用）
             │           │
             ▼           ▼
            用 FB       用 FC（简单省事）
```

快速对照表：

| 情况 | 建议用 | 原因 |
| ---- | ---- | ---- |
| 温度单位换算、线性计算 | FC | 算完就走，无需记忆 |
| 电机启停（要记住"是否在转"） | FB | 需要 Static 保存状态 |
| 同一逻辑控制多台相同设备 | FB | 一台设备一个背景 DB，互不干扰 |
| 报警信息格式化、文本拼接 | FC | 无状态、纯处理 |
| 需要大量中间结果参与下一周期 | FB | Static 数据掉电可保持 |

## 三、形参与实参

程序块要被反复调用，就必须有"接口"——把数据送进去、把结果取出来。这就涉及形参和实参。

### 3.1 什么是形参——"表格模板上的空栏"

类比：公司的**报销单模板**。模板上印着"金额""日期""事由"三个空栏。模板印出来的时候，并不知道你会填什么——这些**空栏**就是**形参**（形式参数）。

在 PLC 中，形参就是块定义时在接口区声明好的参数名称和数据类型，它是块对外服务的"窗口"，是预留的"坑位"。

### 3.2 什么是实参——"每次实际填进去的内容"

张三来报销，填了"500 元、3 月 1 日、出差北京"——这些**具体内容**就是**实参**（实际参数）。

在 PLC 中，调用块时把具体的变量（如 I0.0、Q0.0）或常数连接到形参上，这些具体变量就是实参。

```
                块（相当于报销单模板）
          ┌────────────────────────┐
  实参1 ──┤ 形参「启动按钮」        │
  I0.0    │                        │
  实参2 ──┤ 形参「停止按钮」        │
  I0.1    │                        │
          │ 形参「电机运行」        │── 实参3
          │                        │   Q0.0
          └────────────────────────┘
```

重要规则：**实参的数据类型必须与形参一致**。Bool 形参只能接 Bool 实参（如 I0.0），Int 形参只能接 Int 实参（如 MW20）。

### 3.3 六种参数类型详解

| 参数类型 | 出现在 | 数据方向 | 有无记忆 | 通俗理解 |
| ---- | ---- | ---- | ---- | ---- |
| Input | FC / FB | 进（块内只读） | 无 | 送进来的原材料 |
| Output | FC / FB | 出（块内只写） | 无 | 加工好的产品 |
| InOut | FC / FB | 进+出（可读可写） | 无 | 拿去维修的手表 |
| Static | 仅 FB | 块内部使用 | 有（存在背景 DB） | 车间的仓库 |
| Temp | FC / FB | 块内部使用 | 无（每次调用重新开始） | 一次性草稿纸 |
| Return | 仅 FC | 出 | 无 | 函数的最终答案 |

逐个说明：

1. **Input（输入参数）**：把外部数据"送进"块里，块内只能读它、不能改它。类比：把原材料交给加工车间，车间只管用、不负责退货。典型：启动按钮、设定温度。
2. **Output（输出参数）**：块把结果"递出"去。实参必须是一个能"接住"结果的变量（Q0.0、M0.2、DB 变量），不能接常数。典型：电机运行输出、报警标志。
3. **InOut（输入/输出参数）**：同一个变量既进又出。类比：把手表送去维修——表还是你那块表，但内部零件被改动了。典型：传入一个计数值，块内对它加 1，外面看到的就是加 1 之后的值。注意 InOut 的实参**必须是变量，不能是常数**。
4. **Static（静态参数，仅 FB 有）**：数据存在背景 DB 里，本次调用写入，下次调用还在，还可以设置"保持"（断电不丢）。这是 FB 与 FC 的本质区别所在。典型：电机自锁标志、上次的运行方向。
5. **Temp（临时参数）**：块执行过程中的"草稿纸"，每个扫描周期调用开始时是随机值/无效值，用完就扔。**绝对不要**指望 Temp 变量跨周期记住任何东西。
6. **Return（返回值，仅 FC 有）**：新建 FC 时默认类型为 Void（无返回值）；可以改成 Int、Real 等，此时 FC 就像一个"有答案的公式"。在 SCL 中直接给 FC 名字赋值；在 LAD 中，FC 调用框会多出一个返回值输出引脚。FB 没有 Return 参数。

参数数据流向示意图：

```
            ┌──────────── FC / FB 块内部 ────────────┐
 外部变量 ──►│ Input（只读，原材料）                   │
 外部变量 ◄──│ Output（只写，产品）                    │
 外部变量 ◄─►│ InOut（可读可写，送去维修的手表）        │
            │                                        │
            │   逻辑加工过程：                         │
            │   Temp（草稿纸，内部周转，不保留）        │
            │   Static（仓库，FB 专属，跨周期保存）     │
            └────────────────────────────────────────┘
   Return：FC 的返回值，由 FC 名字本身带回（仅 FC）
```

### 3.4 在 TIA Portal 中定义 FC/FB 参数的步骤

以新建一个 FB 为例：

1. 项目树 → 双击"添加新块" → 选择"函数块 FB" → 输入名称（如"电机控制"，支持中文）→ 语言选 LAD → 点"确定"；
2. 双击打开这个 FB，编辑器上方（或左侧）就是**块接口**区；
3. 在对应区域行中单击单元格，依次填写：**名称、数据类型、（可选）默认值、（可选）注释**；
4. 需要 Static 就在 Static 区添加（FB 才有此区）；
5. 按 Ctrl+S 保存并编译，确认下方"信息"栏没有红色错误；
6. 到调用处（一般是 OB1）：把块从项目树拖进网络 → 对 FB 会弹出"调用选项"对话框 → 填写背景 DB 名称（如"电机1_DB"）→ 确定；
7. 在块的引脚上连接实参：单击引脚输入变量，或从项目树把变量拖到引脚上。

块接口区长这样：

```
┌─ 块接口 ────────────────────────────────────────┐
│ 类型     │ 名称     │ 数据类型 │ 默认值 │ 注释   │
├─────────┼─────────┼─────────┼────────┼────────┤
│ Input   │ 启动按钮 │ Bool    │ false  │        │
│ Input   │ 停止按钮 │ Bool    │ false  │        │
│ Output  │ 电机运行 │ Bool    │ false  │        │
│ InOut   │         │         │        │        │
│ Static  │ 运行标志 │ Bool    │ false  │（FB专属）│
│ Temp    │         │         │        │        │
│ Return  │（仅FC有）│ Void    │        │        │
└─────────────────────────────────────────────────┘
```

## 四、多重背景（Multi-instance）

### 4.1 什么是多重背景

场景升级：现在不是车间有 10 台电机，而是**一台设备里集成了 3 台电机**（比如一条输送线的 3 段传送带）。有两种做法：

- 做法 A：在 OB1 中调用 3 次"电机控制_FB"，生成 3 个背景 DB（电机1_DB、电机2_DB、电机3_DB）。可行，但项目树里 DB 会越来越多，大型项目会"DB 泛滥"；
- 做法 B：写一个"设备控制_FB"，在它自己的 Static 区放 3 个类型为"电机控制_FB"的变量，把 3 次调用全部"装进"这一个父 FB 里。这样 3 台电机的全部数据只占用**一个**背景 DB。

做法 B 就是**多重背景**：把一个 FB 的实例作为另一个 FB 的 Static 变量，实现"块套块"。

使用场景：设备由多个相同部件组成（多轴、多电机、多阀门）；希望整个设备的数据集中在一个背景 DB 中管理。

### 4.2 配置方法

前提：子 FB（电机控制_FB）已经建好、接口定义完毕。

1. 新建父 FB：添加新块 → 函数块，命名"设备控制"；
2. 打开"设备控制"的块接口 → 找到 **Static** 区；
3. 新增一行：名称填"电机1"，**数据类型直接填"电机控制"**（就是子 FB 的名字，下拉列表里能选到）；
4. 同样方法添加"电机2""电机3"；
5. 在"设备控制"的程序区，把 Static 区的"电机1"拖到网络中 → 直接生成调用框（不会再弹背景 DB 对话框，因为数据存在父 FB 的背景 DB 里）→ 连接实参；
6. 编译后打开父 FB 的背景 DB（如"设备控制_DB"），可以看到"电机1.""电机2.""电机3."三组完整数据。

结构示意：

```
              设备控制_FB（父 FB）
┌──────────────────────────────────────────────┐
│ Static 区：                                   │
│    电机1 : 电机控制_FB   ──► 程序中第 1 次调用 │
│    电机2 : 电机控制_FB   ──► 程序中第 2 次调用 │
│    电机3 : 电机控制_FB   ──► 程序中第 3 次调用 │
└──────────────────────┬───────────────────────┘
                       ▼ 编译后只生成 1 个背景 DB
              设备控制_DB（背景 DB）
┌──────────────────────────────────────────────┐
│ 电机1.启动按钮  电机1.电机运行  电机1.运行标志 │
│ 电机2.启动按钮  电机2.电机运行  电机2.运行标志 │

```

## 五、完整案例：用 FB 封装电机控制逻辑

### 5.1 需求描述

封装一个通用的"电机控制"功能块，要求：

1. 启动按钮按下 → 电机运行并自锁（松手后继续运行）；
2. 停止按钮按下 → 电机停止；
3. 故障信号出现 → 电机立即停止并点亮故障指示灯；
4. 故障解除后电机不会自动重启，必须重新按启动按钮；
5. 这个块以后给任何电机调用，一机一份记忆，互不干扰。

### 5.2 接口定义表

| 接口区 | 形参名称 | 数据类型 | 说明 |
| ---- | ---- | ---- | ---- |
| Input | 启动按钮 | Bool | 常开按钮，按下为 1 |
| Input | 停止按钮 | Bool | 按下为 1 表示请求停止 |
| Input | 故障信号 | Bool | 1 = 有故障（如热继电器动作） |
| Output | 电机运行 | Bool | 控制电机接触器 |
| Output | 故障指示 | Bool | 故障指示灯 |
| Static | 运行标志 | Bool | 内部自锁记忆（FB 记忆的核心） |
| Return | —— | —— | FB 没有 Return 参数 |
| Temp | —— | —— | 本例简单，暂不需要 |

### 5.3 FB 内部程序（梯形图 + 文字分析）

FB 名称：电机控制；背景数据由调用时的实例 DB 提供。

```
网络 1：启停自锁控制（核心网络）

      启动按钮          停止按钮         故障信号              运行标志
      (Input)          (Input)         (Input)              (Static)
 +──────| |──────+───────|/|─────────────|/|───────────────────( )──────
 |               |
 |   运行标志     |
 |   (Static)    |
 +──────| |──────+
          (自锁触点)
```

文字分析：

- 停止按钮和故障信号都用**常闭触点（|/|）**：只要它们为 1（请求停止/有故障），能流就被切断；
- 启动按钮按下瞬间，能流通过 → 运行标志线圈得电；
- 运行标志得电后，下方并联的自锁触点（Static 变量）闭合 → 即使松开启动按钮，线圈依然保持得电——这就是"自锁"，而这份"记忆"正是存在背景 DB 的 Static 区里的；
- 一旦停止或故障出现，自锁链条被切断，电机停止；故障消失后也不会自己重新得电，必须再按启动按钮。

```
网络 2：输出电机

     运行标志                                电机运行
     (Static)                               (Output)
────────| |────────────────────────────────────( )──────
```

文字分析：把内部记忆状态送到输出引脚，由调用处决定它最终驱动哪一路输出点。

```
网络 3：故障指示输出

     故障信号                                故障指示
     (Input)                                (Output)
────────| |────────────────────────────────────( )──────
```

文字分析：有故障就点亮故障灯，与电机是否在运行无关。

### 5.4 在 OB1 中调用（调用示例）

在 OB1 中把"电机控制"FB 拖入网络，弹出"调用选项"对话框，背景 DB 填"电机1_DB"，然后连接实参：

```
网络 1：1 号电机（背景 DB：电机1_DB）
                    ┌──────────────────────────────┐
 "启动按钮1" I0.0 ──┤ 启动按钮              电机运行 ├── "电机1"     Q0.0
 "停止按钮1" I0.1 ──┤ 停止按钮              故障指示 ├── "故障灯1"   Q0.2
 "故障信号1" I0.2 ──┤ 故障信号                      │
                    └──────────────────────────────┘
                       （FB：电机控制）
```

```
网络 2：2 号电机（背景 DB：电机2_DB）——同一个 FB 的第二次调用
                    ┌──────────────────────────────┐
 "启动按钮2" I0.3 ──┤ 启动按钮              电机运行 ├── "电机2"     Q0.1
 "停止按钮2" I0.4 ──┤ 停止按钮              故障指示 ├── "故障灯2"   Q0.5
 "故障信号2" I0.5 ──┤ 故障信号                      │
                    └──────────────────────────────┘
```

两台电机调用的是**同一份程序**，但各自的启动/停止状态分别记在电机1_DB 和电机2_DB 里——1 号电机在转，2 号电机照样可以停着，互不干扰。这就是 FB 封装的威力：写一次，用无数次。

### ③ 用监控表模拟输入 / 修改变量的方法

1. 项目树 → PLC_1 → "监控与强制表" → 双击"监控表_1"；
2. 把上面变量清单中的变量逐行添加（或从 PLC 变量表整批拖入）；

5. 模拟按钮动作要"按下再松开"：先把启动按钮1 置 1，观察后再置回 0，这才是真实的按钮操作；
6. CPU 处于 RUN 时修改变量立即生效，无需其他操作。

### ④ 预期结果

| 操作 | 预期结果 |
| ---- | ---- |
| 启动按钮1 I0.0 置 1 | 电机1 Q0.0 立刻变为 1 |
| I0.0 置回 0（松开按钮） | 电机1 Q0.0 保持 1（自锁生效） |
| 停止按钮1 I0.1 置 1 | 电机1 Q0.0 变为 0 |
| 电机运行中把故障信号1 I0.2 置 1 | Q0.0 立刻变 0，故障灯1 Q0.2 变 1 |
| I0.2 置回 0（故障解除） | Q0.2 熄灭，但 Q0.0 保持 0，不会自动重启 |
| 电机1 与电机2 分别操作 | 两者状态互不影响 |

### ⑤ 功能验证清单（逐项打勾）

- [ ] 按启动按钮1，电机1 得电；
- [ ] 松开启动按钮1，电机1 保持得电（自锁）；
- [ ] 按停止按钮1，电机1 失电；
- [ ] 运行中给出故障信号1，电机1 立即失电且故障灯1 亮；
- [ ] 故障解除后电机1 不自动重启，需重新按启动；
- [ ] 故障信号出现时即使还按着启动按钮，电机也不运行；
- [ ] 电机2 独立完成上述全部测试，与电机1 互不干扰；
- [ ] 打开电机1_DB 能看到"运行标志"随电机启停变化（体会 Static 的记忆作用）。

### ⑥ 结果不符时的排查方法

1. **电机不自锁**：检查自锁触点是否并联在启动按钮两端、是否用的 Static 变量"运行标志"；如果误用了 Temp 变量，每次调用都会丢失记忆；
2. **两台电机互相干扰**：说明两次调用用了同一个背景 DB，或把实参接成了相同变量；检查背景 DB 名称和引脚连接；
3. **故障时电机不停**：检查故障信号是否接在常闭触点 |/| 上，且该触点在自锁回路的主干上；
4. **调用框上出现红色/提示"调用版本不一致"**：修改 FB 接口后未重新编译，右键该块选择"编译"，或删除旧调用重新拖入；
5. **修改变量没反应**：确认监控表已点"监控"，且 CPU 在 RUN 状态；确认修改值后按了回车；
6. **下载失败**：检查 PLCSIM 是否已启动完成、接口类型是否选的 PLCSIM，先编译后下载。

## 📌 本章小结

1. 程序块的两大价值：**代码复用**（写一次用 N 次）和**结构清晰**（一个块管一件事）；
2. 四种块各司其职：**OB** 是程序入口（OB1 主循环、OB100 启动一次、OB30 循环中断），由 PLC 自动调用；**FC** 无记忆做计算；**FB** 有记忆做设备控制；**DB** 存数据（全局 DB 是公共仓库，背景 DB 是 FB 的私人仓库）；
3. 选型口诀：**要记状态用 FB，纯算一下用 FC**；
4. 形参是块的"接口空栏"，实参是调用时填入的具体变量；六种参数类型中，Input/Output/InOut 是对外的进出口，Static 是 FB 的记忆，Temp 是草稿纸，Return 是 FC 的答案；
5. 多重背景把子 FB 实例放进父 FB 的 Static 区，多台设备共用一个背景 DB，大型项目的标准做法；
6. 用 FB 封装电机控制的套路：定义接口 → 写内部逻辑（自锁用 Static）→ 调用时一机一背景 DB。

---

## ⚠️ 常见错误与注意事项

1. **在 FC 里找 Static 区**：FC 没有 Static，也没有背景 DB。需要记忆的必须用 FB；
2. **用 Temp 变量保存跨周期数据**：Temp 每次调用都是"新草稿纸"，上一周期的值不可信。跨周期记忆只能用 FB 的 Static（或全局 DB）；
3. **实参与形参数据类型不一致**：Bool 引脚接了 Int 变量会直接报错。连接引脚时看清类型；
4. **InOut 参数接了常数**：InOut 必须是变量（它要被块修改后"还回来"），接常数无意义且会报错；
5. **Output 接了常数**：输出实参必须能"接住"结果，应接 Q、M 或 DB 变量；
6. **修改了 FB 接口后忘记重新编译**：调用处会显示版本不一致（红色提示），重新编译块即可；
7. **FB 调用时漏建/误删背景 DB**：程序无法编译。重新拖入 FB 并填写背景 DB 名称；
8. **把周期性任务写进 OB100**：OB100 只在启动时执行一次，放循环任务等于只跑一遍；
9. **多重背景类型填错**：Static 变量的数据类型必须与子 FB 的名称完全一致，选错会导致调用失败；
10. **滥用全局 DB 当"万能口袋"**：所有块都随便读写一个全局 DB，短期方便、长期失控。属于某设备的专有数据应放背景 DB。
